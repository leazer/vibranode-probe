# COM13 / J-Link 首轮实板通信

## ADXL线缆字节序勘误

TAB5 codec实现前的交叉核对发现，冻结协议和黄金向量要求ADXL每轴以3字节小端低20位发送，但固件曾直接复制芯片FIFO的大端寄存器字节，`pc_host.py`也按相同错误格式解码。两端因此能互通，却不符合协议且会使独立TAB5实现得到错误数值。

固件现显式剥离FIFO标记并转换字节序；测试用芯片FIFO值`FF 5D 81 / 00 A8 C0 / 0C 22 40`，线缆必须得到`D8 F5 0F / 8C 0A 00 / 24 C2 00`，对应`-2600 / 2700 / 49700`。PC脚本同步改为小端低20位符号扩展。13项仿真回归、6项PC测试和自检通过；模式0完整Rebuild 0错0警，Code53620/RO2324/RW16/ZI29792。

修复镜像已由J-Link烧录并校验。COM13、4Mbps、slow配置5秒：STOP边界ADXL1219/ICM954，最终捕获1220/955，姿态856；三路均segment1且相邻序号连续，CRC错误0。首个ADXL线缆样本`8A F1 0F / 99 0B 00 / F3 C1 00`解码为`(-3702, 2969, 49651)`，静止量级合理。捕获文件`tests/build/com13-adxl-wire-fixed.bin`。旧捕获文件保留旧布局，只能按修复前脚本解码。

## STOP 最终边界闭环

STOP 改为异步完成：收到请求后先停止双路采样与姿态链，等待 ADXL 和 ICM 都报告 `stopped`，再读取并返回两路 `last_sequence`。停止期间同 request_id 重试不重复执行，不同控制请求返回 BUSY；响应发送成功后才写入幂等缓存。这样返回的边界包含停止时仍在途的最后一批数据。

协议测试覆盖延迟响应、双路最终状态、双路末序号和停止期间重试；全部 13 项宿主/仿真组件回归通过。模式0完整 Rebuild 0错0警：Code44688/RO2324/RW16/ZI28832，SRAM 余量约3.8KB；J-Link烧录并校验成功。

COM13、4Mbps、slow配置8秒实测：STOP边界ADXL1977/ICM1555，最终捕获样本1978/1556，恰好覆盖序号0至边界；TIME_INFO8、STATUS16、CRC错误0。文件`tests/build/com13-stop-boundary.bin`。

## 高采样率瓶颈排查

4Mbps默认配置5秒，GET_STATUS：ADXL交付3950、queue_drops16075；ICM交付6223、queue_drops32999；两路SPI/overflow/format/unknown_gaps均0，队列均满4槽。PC FETCH平均14.15ms、最大251ms（含超时窗口）。确定缺口来自原始队列满而非收到的帧CRC错误。

逐步实板实验：读后按2ms调度减少小批次；FETCH额度1600改16000进一步提高交付；PC非阻塞读取达到约3254/6159 SPS但仍缺口。延长4ms产生ADXL FIFO溢出，保持窗口等待也未解决。所有本轮实验固件改动已撤回，恢复已验证4Mbps兼容版并重新烧录；采集与协议回归恢复通过。实验主机设置只在临时进程生效，pc_host默认未改变。

下一步需设计软件批次合并/按字节利用队列、记录USB窗口延迟分布并优化主机读取；不能简单延迟硬件FIFO读取或扩大队列槽数。当前高采样率全量上传仍未修复。

## 最新：4 Mbps兼容档实测

用户确认USB转串口不支持5Mbps，授权增加4Mbps。保留1/5Mbps和原掩码bit0/bit1，新增bit2=4Mbps，SET_LINK接受4000000。协议测试先失败后通过，模式0构建0错0警：Code44456/RO2324/RW16/ZI28824；J-Link烧录及校验成功。

4Mbps slow/10秒：切速GET_STATUS确认成功，配置/START/STOP成功，ADXL2485/ICM1959，TIME_INFO10/STATUS20，CRC零；捕获两路单段、序号无缺口。文件tests/build/com13-4m-slow.bin。

4Mbps default/10秒：切速与命令成功，但ADXL仅7654（757/s）、ICM12495（1236/s），全部时间不确定，CRC仍零。离线检查ADXL423处、ICM571处不连续，频繁换段；高速默认组合吞吐未通过。文件tests/build/com13-4m-default.bin。下一步排查批次粒度、队列容量与主机FETCH效率，不能将4Mbps基本通信成功等同4k/8k全量上传成功。

J-Link 设备名 `-AT32F413CCU7`，SWD 1 MHz，S/N 20721562；PC COM13 为 CH343。

## 修复与证据

- 协议入口遗漏 UART 初始化，USART 引脚有波形但 RX DMA 未启动；补齐后 HELLO 成功。
- PC 请求缺少统一 request_id：SET_CONFIG 少4字节，其他命令编号不匹配。统一编码，GET_STATUS按当前115字节快照解析。
- 固件发送窗口不等待 DMA 完成，send失败仍释放原始队列。现在每轮至多启动一帧，忙时保留队列，FETCH_DONE发送成功才结束窗口。
- PC FETCH固定等待200ms、4096字节定长读取和START后额外等待造成取数不及时。改为及时读取可用字节，FETCH_DONE到达即结束窗口。

协议与UART ARM仿真、PC三项测试通过；协议测试覆盖TX忙时不释放两路批次。模式0 Rebuild 0错0警：Code44444/RO2324/RW16/ZI28824。已用J-Link烧录并校验，校准区烧录前后4096字节完全一致。模式3专用水位验证脚本不适用于模式0（未链接probe_stack_capacity），不能计为本次通过项。

## 实板结果

1 Mbps slow，10秒：HELLO/SET_CONFIG/START/STOP成功。控制台ADXL2484、ICM1957，TIME_INFO10、STATUS20、CRC错误0；捕获文件ADXL2483、ICM1957（最终排空尚未写入dump，故差1）。捕获两路segment均1、相邻样本序号连续，无中间缺口。仍需完善STOP最终排空和统计口径，不能将本次短测等同长期验收。

5 Mbps：RTT确认切速，3秒无有效帧后回退1 Mbps。PC串口调用卡住，测试进程终止后COM13仍拒绝打开；已请求拔插USB-RS485后复测。尚未确认5 Mbps双向通讯或吞吐。

原始记录位于忽略目录tests/build：com13-slow-paced.bin、com13-ram-after.bin、com13-calibration-before.bin、com13-calibration-after.bin。

## 用户调整：固定1 Mbps

后续用户授权再次测5Mbps：以slow配置隔离吞吐因素，1Mbps HELLO成功（session=0x1D8AB7D7），PC设置5Mbps后GET_STATUS无有效应答，回退串口调用再次卡住，已终止本次测试进程。RTT记录479607ms切到5Mbps、482607ms自动回退。回退后SRAM确认current_bps=1000000、UART errors=0、bad_types/bad_sessions=0；RX位置已由回退初始化清零，不能据此断言5Mbps期间完全无字节。当前5Mbps双向通信未通过，不能归因为硬件带宽；下一步需要高速期间原始RX捕获及示波器确认PC实际位宽/方向切换。J-Link RAM快照tests/build/com13-5m-ram.bin。

用户要求暂停5Mbps，优先验证1Mbps；不能据PC调用卡住断定硬件不支持5Mbps。COM13随后已恢复打开，无需继续等待拔插。

连续执行30秒和60秒独立会话，均HELLO/配置/START/STOP成功。30秒控制台ADXL7541、ICM5968，TIME_INFO30/STATUS60；60秒ADXL15125（252/s）、ICM11984（200/s），TIME_INFO60/STATUS120。两次CRC零，两路捕获均segment1、相邻序号连续。60秒捕获已包含最终排空，样本数与控制台一致，STOP边界15124/11983与最后样本序号一致。启动时间不确定帧ADXL24、ICM166，此后消除。

增加tests/check_capture_continuity.py用于离线检查。下一步1Mbps更长时及异常恢复验证；5Mbps挂起。当前只验证ADXL250/ICM200配置，不能用1Mbps承载默认4k/8k全量流。

## 2026-09-10 批量成帧（TAB5 联调反馈回灌探头侧）

TAB5 实测定位：慢速 ODR 每次 FIFO 读取入队 1 样本批次（每样本 32B 线缆头开销 ~78%），4 槽协议队列溢出即断段重置序号；TAB5 侧读凑包修复+拉流泵（见 TAB5 仓库 2026-09-10 里程碑）把交付率拉到 90-97% 后，残余 ~3% 丢样仍源于此。

本仓库提交 `5badb1f`：accept_batch 将同段、序号连续、≤512B 槽上限、40ms 窗口内的连续读取合并进同一队列槽（attitude 旁路保持逐读取视图）；慢速 ODR 帧率降 ~25 倍，头开销 ~26%（40ms 窗口）且不再打爆队列。RAM 零增量（槽内追加，Code=53920/ZI=29792）。回归：新增 run_probe_acquisition.py（此前该状态机测试无 runner，stub 补 EXINT 符号），断言合并槽 56 样本/504B、attitude 逐读取 16 包、250ms 无排水才出现满队丢样；time/spi/agm/pc_host 全部 PASS，Keil Rebuild 0错0警。

待实板验证：J-Link 重烧后 TAB5 Slow 复测（预期探头 drop≈0、gap=0、批次 count≈10）；4k/8k 在 5Mbps 复测（理论线上 ~200KB/s < 500KB/s，应可通过）。已确认 AT32F413 支持 EOPB0 配置 64KB SRAM（库含 usd_type.eopb0 但无 helper），后续如需更深队列可一次性编程 option byte + 调整 MDK IRAM，值需以 AT32F413 RM 为准。
