# 2026-09-10 EOPB0 64KB SRAM 与批次上限对齐线缆帧

## 背景与动机

TAB5 侧 4k/8k @ 5Mbps 实测交付率 93.6% / 83.8%，残余丢样定位为探头原始队列丢样
（`[linkval]` 探头计数 drop 持续增长，SPI/溢出/格式错误为零）。两个结构性约束：

1. 原始队列槽 `data[512]`：ICM 8k 时一个槽只装 32 样本（512B），4 槽共约 16ms
   缓冲，深连接水即丢、断段重置序号。
2. 合并上限沿用槽容量 512B：一个槽对应一帧，帧越小则 5Mbps 线缆上每字节
   承载的帧头/CRC 开销越大，且发送节奏受主循环每次 poll 一帧限制。

用户确认 AT32F413CCU7 的 EOPB0 可将 SRAM 配为 64KB（默认 32KB + 32KB
flash 访问 SRAM），本里程碑把镜像改为 64KB 布局并放宽上述两个约束。

## 线缆帧上限分析（冻结协议）

`try_send_stream` 一批一帧：帧总长 = 19 + 32 + samples×per_sample，
载荷上限 `PROBE_FRAME_PAYLOAD_MAX = 1005`：

- ADXL 9B/样本：`floor(973/9) = 108` 样本上限（载荷 1004）。
- ICM 线缆 13B/样本：`floor(973/13) = 74` 样本上限；但槽内保存原始 16B
  FIFO 包，`data[1024]` 时槽上限为 `1024/16 = 64` 样本（载荷 864）。
  512B 单次读 = 32 样本，两次读合并即到 64，提高 `data` 不改变实际槽容量，
  故取 1024B 而非 1184B。

## 变更

### 1. EOPB0 启动早期守卫（`project/src/probe_eopb0.c`，新增）

镜像按 64KB 链接后，若芯片仍是出厂 32KB 配置，`__main` 的 scatter load 会在
`main()` 之前把 ZI 清进不存在的内存。因此守卫必须先于 C 运行时执行：

- `Reset_Handler`（`startup_at32f413.s`）开头先把 MSP 驻留在保证存在的低
  32KB（0x20007C00），调用 `probe_eopb0_early_config`，返回后恢复
  `__initial_sp` 再进 `SystemInit`/`__main`。
- `probe_eopb0_early_config` 读 `USD->eopb0`（0x1FFFF810）：已是 `0xFA`
  直接返回（每轮上电仅一次字节读的开销）。
- **编程流程按 Artery AN0026（Extending SRAM in User's Program）**：
  `flash_unlock()` → `flash_user_system_data_erase()` →
  `flash_user_system_data_program(eopb0, 0xFA)` → `nvic_system_reset()`。
  **首版实板教训：漏掉 `flash_unlock()` 时 USD 解锁位 `usdulks` 永不置位，
  库函数在 `while(ctrl_bit.usdulks==RESET)` 死等**（J-Link 仿真实测卡死；
  USD 未被改动，重烧即恢复）。
- LED 时间线（低电平点亮，与 probe_led 同接法）：
  - 紫色 4 闪：守卫介入，即将编程；
  - 熄灭约 50ms：USD 擦除+编程进行中；
  - 紫色 ~4Hz 约 2 秒：编程并回读校验通过，随后 `nvic_system_reset()`
    使 option byte 重载；
  - 红色 ~8Hz 常闪：回读校验失败；
  - 完全无灯：卡死在 flash 库内部，需回报。
- 若复位后芯片仍以 32KB 运行（option byte 未随系统复位重载的兜底），
  断电重上电一次即生效；守卫按存储值判断，不会重复编程。

### 2. Keil 工程 IRAM 0x8000 → 0x10000（`VibraNode.uvprojx` 三处）

`<Cpu>` 描述串、`<IRAM>`、`OCR_RVCT9` 同步修改；登记 `probe_eopb0.c`。

### 3. 槽扩容 + 线缆样本上限合并

- `probe_raw_batch.data` 512 → 1024（`probe_acquisition.h`）。
- `probe_acquisition.c` 新增 `ADXL_BATCH_SAMPLES=108`、`ICM_BATCH_SAMPLES=64`，
  `accept_batch` 合并条件在原有（同段、序号连续、容量、40ms 窗口）基础上
  增加 `batch->samples + samples <= batch_cap`。
- 单次 FIFO 读上限保持 512B 不变（56 ADXL / 32 ICM 样本，均低于槽上限），
  ICM 批首时间的 backlog 年龄修正（`ACQ_COUNT_WAIT` 中 512 参照）不受影响。
- 姿态旁路仍为逐读取视图（≤512B），只是槽结构随 `data` 变大。

### 4. 回归更新

`tests/test_probe_acquisition.c` 合并断言随上限调整：7 次读 504B 槽改为
13 次读 104 样本/936B 槽（第 14 次读因 104+8>108 开新槽）。

## 实板记录

- **首版（无 `flash_unlock()`）J-Link 仿真卡死**：库函数
  `flash_user_system_data_erase()` 在 `while(ctrl_bit.usdulks==RESET)`
  死等，断电重启仍卡同一处（EOPB0 未写成，64KB 镜像每次上电都重试）。
  按 AN0026 补 `flash_unlock()` 后待实板复测。

## 未上板事项（不能当作硬件验收）

- **EOPB0 编程路径本身尚未在修复版上实板验证。** J-Link 烧录本版后
  **脱离调试器直接上电**观察：
  1. 紫色 4 闪 → 短暂熄灭（擦除+编程）→ 紫色 ~4Hz 约 2 秒 → 自动复位；
  2. 复位后应正常启动（灯语正常）。若复位后未启动，断电重上电一次；
  3. 红色 ~8Hz 快闪=校验失败；完全无灯=卡死在 flash 库内部，回报现象。
- 4k/8k @ 5Mbps 交付率需在 TAB5 侧重测（`[linkval]` 每秒行 + 探头计数），
  预期探头 drop 显著下降、批次 count 增大；若仍有残余丢样，下一个旋钮是
  `QUEUE_SLOTS`（RAM 余量充足）。
- 64KB SRAM 模式会关闭 32KB flash 加速 SRAM，flash 取指增加等待周期；
  `PERF` 计数（acq/attitude/loop 最大耗时）上板后需对比确认无回退。
