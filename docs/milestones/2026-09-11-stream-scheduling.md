## 根因：三路严格轮转的份额上限

`window_service` 每个主循环 poll 只发一帧，ADXL/ICM/ATT 轮转——每路最多
1/3 帧率。实测帧率上限 ~940 帧/s（48 窗/s × 20ms 窗 × ~1 帧/poll），ICM
天花板 ≈ 313 帧/s × 饱和期平均 ~21 样本/槽 ≈ **6570 样本/s，与实测 6500/s
吻合**。（8k 时 query_interval 2000µs 下单次 FIFO 读仅积到 ~336B=21 样本；
槽饱和时合并被断段打断，无法成长到 64。）

## 变更（`probe_proto.c` window_service）

服务成功后不再固定轮转：**原始流若仍持有更大积压（queued_bytes，经
`probe_acquisition_get_status` 读取）则原地连发**，否则照常轮转；姿态保持
原轮转槽位。效果：饱和时 ICM 拿到大部分帧（排空速度 2-4 倍于生产），队列
变浅后合并恢复、槽长回 64 样本，所需帧率降到 ~125/s，死循环解除；慢速 ODR
队列为空时行为与原轮转一致。

## 回归更新（`test_probe_proto.c`）

1024B 槽后无人排水的队列会合并出大帧（ADXL 104 样本=987B、ICM 64=883B），
两帧合计超过旧测试的 1600B 窗口预算，且 `len == 32+8*9` 精确断言失效：

- FETCH 预算 1600 → 4096（真实 TAB5 用 16384，此处对齐量级）。
- g 节尺寸断言改为按帧内 count 字段自洽：ADXL `len == 32+count*9`
  （count ≥ 8，上限 104）；ICM `len == 32+count*13`（count ≥ 16，上限 64）。
- k 节（排水后新鲜批次）尺寸断言保持 8/16 样本不变。

## round-13 实板与队列加深（同日第二轮）

调度修复实板生效但未收敛：4k/8k@5M ADXL 96.9%→**98.1%**、ICM 81.2%→
**87.5%**，探头 drop 减半（s2 15666→9511）、断段 3283→2025；批次仍以
11-29 样本为主（count 64 仅偶现）。

结构性平衡点：发射上限 ~860 帧/s（探头主循环 1 帧/poll × 48 窗/s × ~96%
占空），小槽需求 = 8000/20 + 4000/14 + 姿态 160 ≈ 887 帧/s **> 860**——
系统贴着赤字边缘运行，队列反复满 → 丢样 → 断段 → 槽无法长到 64 → 需求
降不下来。打破循环需要吸收瞬时突发，而这正是 64KB SRAM 买来的余量：

- `QUEUE_SLOTS` 4→8、`ATT_SLOTS` 2→4（`probe_acquisition.c`）。
- ZI 35936 → **48992**（+13056，与手算一致；64KB 内余量 ~16KB）。
- 五项回归 PASS（250ms 无人排水丢样场景在 8 槽下仍成立）；Rebuild 0 错
  0 警 Code=54700；四模式验证（模式 2 ZI=34448）。

预期：突发被吸收 → 丢样/断段骤降 → 合并完成 → 槽到 64 → 需求 ~420 帧/s
远低于上限 → 稳态。若复测 ICM 仍 <100%，下一层是降低 8k 档的
`query_interval` 读取间隔让单次读直接逼近 512B（32 样本），减少合并依赖。

## round-15 实板与 ICM 读节流（同日第三轮）

TAB5 泵节流（probe 明细行 5s）后 ICM 丢样纹丝不动（~520/s），泵停顿假说被
推翻；ADXL 则收敛到探头侧近乎完美（s1 全场 drop 10、断段 4、接受率≈100%，
交付 98.8%）。批次日志给出真因：**背靠背 FIFO 读每次只抓 1-2ms 数据**
（10-30 样本），小槽形态下帧需求 ~940 帧/s > 发射上限 ~820 帧/s；且队列越
浅新槽越没有合并伙伴，合并机制救不了场。

修复（`probe_acquisition.c`）：ICM ≥4k 的读按 ~512B 节流（8k→4ms=64 样本
=一整个线缆帧），一次读即一帧，需求降到 ~125 帧/s；被 FIFO 读上限截断的
读（backlog）自动切回连续排空。ADXL 保持 2ms 短间隔（其 288B FIFO 填充
本就小、从未饱和队列，且 proto 回归的时间估计器装置依赖现有节奏）。
ACQ_COUNT 的门控改为纯 due_us（原"新 IRQ 边缘即读"的捷径会绕过节流；
batch_irq_us 锚定语义不变，仍取最新边沿）。

验证：五项回归 PASS（采集回归断言 104/936 合并槽、4ms 节流下单读 16 样本、
realtime 200→2000 tick 适配 4ms 节奏；proto 回归 k 节 tick(4)→tick(120)、
尺寸断言按 count 自洽——固定 24B 假 FIFO 在 8ms 节流下 fiction 速率不一致，
故 ADXL 不节流）。Rebuild 0 错 0 警 Code=54756 / ZI=48992；四模式验证。

预期（board round 16）：ICM 读 64 样本/帧、帧需求 ~640 帧/s（含 ADXL/姿态/
控制），余量 ~180 帧/s；探头 ICM drop→0，交付→98%+（剩余为 5M 线路
uart/crc 损耗）。若 FIFO 在探头主循环长停顿（>12ms）下溢出，考虑给
`query_interval` 加动态收缩或提高读上限。

## round-16 实板与窗口连发（同日第四轮）

读节流到位：批次日志出现 ADXL count 103-108、ICM 59-63 的满槽帧，ADXL
交付 **99.8%**（探头侧 drop 仅 105）。但 ICM 反而恶化到 85.4%（drop
~1087/s），且帧率从 ~820 掉到 ~370 帧/s——大帧每帧 ~1.5ms 线缆时间，
"一 poll 一帧"规则把主循环节奏变成了硬上限（~370 fps），恰好又压在
降低了的需求上，而线缆本身 ~75% 空闲。

修复（`probe_proto.c` window_service）：窗口内**连发**——每帧发完后
只等该帧自己的 DMA 完成（`probe_uart_poll` 处理完成与 DIR 回转，纯线缆
时间），随即立刻尝试下一帧，直到队列/预算/窗口到期/状态周期结束。发射
上限从"循环周期"回归"线速"（理论 ~600+ 帧/s 满帧）。

验证：五项回归 PASS；Rebuild 0 错 0 警 Code=54836 / ZI=48992；四模式
验证通过。

预期（board round 17）：帧率恢复 ~500-600 帧/s（满帧），ICM 交付 →98%+
（剩余为 5M 线路 uart/crc 损耗）；姿态从 48/s 恢复到 150/s 以上。
若 ICM 仍 <98%，剩余通道为线路信号（查终端电阻/线缆/转换器）或
TAB5 RX 环写满（rxhw 480/489 接近容量，可考虑加大 RX 环）。
